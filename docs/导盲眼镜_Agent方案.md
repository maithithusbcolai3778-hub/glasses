# 导盲眼镜 Agent 系统方案（含 IMU 姿态 + 扩展识别目标）

> 基于现有硬件：ESP32-P4 + OV5647 + 扬声器 + ATK-MS601M 六轴陀螺仪 + 带 NVIDIA GPU 的 PC  
> 方案定位：可快速验证的原型，后续可逐步迁移到独立可穿戴设备

---

## 1. 项目目标

做一个能辅助视障人士出行的原型眼镜：

- **识别前方目标**：
  - 行人、车辆（汽车/公交车/卡车/摩托车/自行车）
  - 红绿灯及颜色状态
  - 盲道、斑马线、道路/可通行区域
  - 障碍物（路桩、垃圾桶、台阶、坑洼、悬空物等）
  - 路牌/文字信息

- **姿态感知**：
  - 通过六轴陀螺仪获取头部姿态（Roll / Pitch / Yaw）
  - 把画面中的目标位置映射到真实方向（左前方 / 正前方 / 右前方）

- **路径引导**：
  - 有盲道时：引导沿盲道行走
  - 无盲道时：基于道路/可通行区域分割，给出局部可通行方向
  - 有障碍物时：给出绕行方向

- **语音播报**：把识别结果和引导建议用中文自然语言播报

> **注意**：本方案中的“道路规划”指的是**基于摄像头的局部可通行方向引导**。如果需要“从 A 地到 B 地”的全局导航，还需要 GPS 和地图数据。

## 3. ATK-MS601M 陀螺仪说明

### 3.1 基本特性

- 内置 ICM-20602 六轴传感器 + STM32 解算单元
- 已做传感器融合，直接输出姿态角
- 通信接口：**UART**，默认波特率 **115200**
- 供电：3.3V / 5V 兼容
- 输出频率：1Hz ~ 250Hz

### 3.2 与 ESP32-P4 连接

```text
ATK-MS601M      ESP32-P4
VCC  ─────────  3.3V/5V
GND  ─────────  GND
TX   ─────────  UART_RX (ESP32)
RX   ─────────  UART_TX (ESP32)
```

### 3.3 数据帧格式

模块自动通过 UART 发送数据帧，格式为：

```text
0x55  0x55  ID  LEN  DATA[N]  SUM
```

常用帧类型：

| ID | 含义 | 数据长度 | 说明 |
|----|------|----------|------|
| 0x01 | 姿态角 | 6 字节 | Roll / Pitch / Yaw |
| 0x02 | 四元数 | 8 字节 | Q0~Q3 |
| 0x03 | 原始数据 | 12 字节 | 加速度 + 角速度 |

姿态角换算：

```text
Roll  = ((RollH << 8)  | RollL)  / 32768 * 180  度
Pitch = ((PitchH << 8) | PitchL) / 32768 * 180  度
Yaw   = ((YawH << 8)   | YawL)   / 32768 * 180  度
```

### 3.4 在本方案中的作用

1. **目标方向映射**：知道用户头部朝向，画面左侧 = 真实左前方
2. **路径引导**：记录相对转向角度，告诉用户“向左转 15 度”
3. **防抖辅助**：结合姿态变化，辅助判断画面抖动或用户是否在移动
4. **跌倒检测**：通过加速度和姿态突变检测摔倒（可选）

## 5. 各组件职责

### 5.1 ESP32-P4 端

- **图像采集**：通过 OV5647 拍照，压缩为 JPEG
- **IMU 采集**：通过 UART 读取 ATK-MS601M 的姿态角
- **网络服务**：提供 HTTP 接口
  - `GET /capture`：返回当前 JPEG 图片
  - `POST /play`：接收文本，驱动扬声器播放
- **音频输出**：播放 PC 发来的中文提示

### 5.2 PC Agent 端

- **图像接收**：从 ESP32 获取图片
- **目标检测**：YOLOv8 检测行人、车辆、红绿灯、盲道、障碍物、斑马线等
- **道路分割**：分割出可通行区域和不可通行区域
- **路径规划（局部）**：
  - 有盲道：沿盲道中心线引导
  - 无盲道：在可通行区域中找最安全的中心方向
- **方向计算**：结合摄像头视场角（FOV）和 IMU Yaw，把画面位置转成真实转向角度
- **大模型调用**：复杂/不确定场景调用 Qwen-VL 进行综合推理
- **语音文本生成**：生成一句自然、简洁的中文提示
- **发送播报**：把文本发给 ESP32-P4 播放

### 5.3 云端大模型

- **模型**：`qwen-vl-plus`（默认），复杂场景升级到 `qwen-vl-max`
- **输入**：原图 + 结构化检测结果 + IMU 姿态 + 当前意图
- **输出**：一句中文安全提示或引导建议
- **触发条件**：只在复杂/遮挡/多目标/不确定场景调用

| 目标类别 | 检测方式 | 说明 |

| 车辆 | YOLO 检测 | 汽车、公交车、卡车、摩托车、自行车 |

| 盲道 | YOLO 检测 / 语义分割 | 识别黄色/灰色凸起盲道 |
| 斑马线 | YOLO 检测 / 语义分割 | 人行横道 |
| 道路/可通行区域 | 语义分割 | 提取地面可走区域 |
| 障碍物 | YOLO 检测 | 路桩、垃圾桶、台阶、坑洼等 |

## 7. 工作流程

```text
1. 触发（按键 或 定时器，建议 0.5~1 秒一次）
        ↓
2. ESP32-P4 同时获取：
   ├── OV5647 拍照
   └── ATK-MS601M 读取 Roll/Pitch/Yaw
        ↓
3. 图片 + IMU 数据通过 Wi-Fi 传给 PC Agent
        ↓
4. PC Agent 并行处理：
   ├── YOLO 检测：车辆/行人/红绿灯/盲道/障碍物/斑马线
   ├── 分割模型：提取可通行区域
   └── OCR（可选）：读取路牌
        ↓
5. Agent 决策：
   ├── 危险情况（如近距离车辆）
   │     → 直接紧急播报，不走大模型
   │
   ├── 有盲道
   │     → 计算盲道中心偏移
   │     → 播报："沿盲道直行" / "盲道向左偏，请向左转 10 度"
   │
   ├── 无盲道但有可通行区域
   │     → 找最大可通行区域的中心方向
   │     → 播报："前方无路沿，请向左转 15 度绕行"
   │
   ├── 复杂/遮挡/不确定
   │     → 把原图 + 检测结果 + IMU 姿态发给 Qwen-VL
   │     → 大模型返回综合判断
   │     → 播报最终结论
   │
   └── 什么都没检测到
         → 周期性播报："前方安全，可慢行"
```

## 8. 局部路径引导策略

### 8.1 有盲道时

1. 检测盲道区域，拟合盲道中心线
2. 计算盲道中心相对于画面中心的水平偏移
3. 结合摄像头水平视场角，换算成需要转向的角度
4. 结合 IMU Yaw 记录当前朝向，给出相对转向指令

**播报示例**：

> "检测到盲道，请沿盲道直行。"
> "盲道向左偏，请向左转 10 度。"

### 8.2 无盲道时

1. 用分割模型提取地面可通行区域
2. 去除障碍物覆盖区域
3. 在可行走路径中找最宽、最连续的区域
4. 计算其中心方向，给出转向建议

**播报示例**：

> "未检测到盲道，前方可通行，请直行。"
> "前方右侧有障碍，请向左转 15 度绕行。"

### 8.3 方向计算

```text
画面中心偏移（像素）    摄像头水平视场角
转向角度 ≈ ─────────────────────── × ─────────────────
               画面宽度                  2
```

例如：
- 画面宽度 640 像素
- 目标偏离中心 100 像素
- 水平视场角 60°

转向角度 ≈ (100 / 640) × 60° ≈ 9.4°

结合 IMU Yaw，可以告诉用户：

> "你的左前方 10 度有车辆，请停下等待。"

## 9. 通信协议

PC 与 ESP32-P4 之间采用 **HTTP REST** 通信。

### ESP32-P4 提供接口

| 接口 | 方法 | 功能 |
|------|------|------|
| `/capture` | GET | 返回当前 JPEG 图片 |
| `/play` | POST | 接收 `text` 字段，播放中文语音 |

### 上行数据（ESP32 → PC）

建议一次请求同时包含图片和 IMU 数据：

```text
POST /perception
Content-Type: multipart/form-data

image: JPEG 图片
yaw:   当前航向角
pitch: 当前俯仰角
roll:  当前横滚角
```

### 下行数据（PC → ESP32）

```json
{
  "text": "前方 5 米有汽车，请停下等待"
}
```

## 10. 开发阶段

### 第一阶段：基础感知闭环（3~5 天）

目标：ESP32 拍照 + IMU 数据传给 PC，PC 跑 YOLO 检测，ESP32 播报结果。

- ESP32 实现摄像头拍照、IMU UART 读取、HTTP 服务
- PC 接收图片 + IMU，跑 YOLOv8n 检测行人/车辆
- 把检测结果转成一句话播报

### 第二阶段：路径引导 + 扩展目标（5~7 天）

目标：加入盲道、斑马线、道路分割、障碍物检测，给出局部路径引导。

- 训练/准备盲道、斑马线、障碍物数据集
- 加入道路/可通行区域分割模型
- 实现盲道跟随和无盲道时的方向引导
- 结合 IMU 给出真实转向角度

### 第三阶段：Agent + 大模型（3~5 天）

目标：复杂场景调用 Qwen-VL，提升系统智能性。

- 设计决策规则：什么时候直接播报，什么时候调大模型
- 接入 Qwen-VL API
- 把检测结果、分割图、IMU 姿态一起传给大模型
- 处理超时、失败等异常情况

### 第四阶段：优化与本地化（2~4 周，可选）

目标：降低延迟、减少成本、提升独立性。

- 把 YOLO 小模型量化，迁移到 ESP32-P4 本地跑
- 优化分割模型速度
- PC 只负责大模型调用
- 探索用手机替代 PC 的可能性

假设使用 `qwen-vl-plus`：

| 项目 | 估算 |
|------|------|
| 一张 512×512 图片 token 数 | 500~1000 tokens |
| 输入成本 | 约 ¥0.0004 / 张 |
| 输出成本（短句） | 约 ¥0.0001 / 次 |
| 单次大模型调用合计 | 约 ¥0.0005 / 次 |
| 连续 1 张/秒，1 小时 | 约 ¥1.8 / 小时 |

> 注意：简单场景（如直接检测到车辆）**不走大模型**，所以实际成本会远低于上面的连续估算。

## 12. 风险与应对

| 风险 | 应对 |
|------|------|
| 网络不稳定，大模型调用失败 | Agent 具备 fallback：小模型结果可直接播报 |
| 延迟高，不适合紧急避障 | 近距离车辆等危险情况直接由 YOLO 触发，不走大模型 |
| PC 没电或不在身边 | 第一阶段仅在室内/短距离验证；后续再考虑本地化 |
| 图片传输慢 | 降低摄像头分辨率、压缩 JPEG 质量 |
| 小模型误检 | 设置置信度阈值，必要时交给大模型二次确认 |
| 盲道识别不准 | 增加训练数据，或用颜色+纹理特征辅助 |
| 无 GPS 无法全局导航 | 本方案只提供局部路径引导；全局导航需加 GPS + 地图 API |
| IMU 漂移 | ATK-MS601M 已做内部融合，Yaw 漂移相对较小；可定期以摄像头检测到的道路方向校准 |

---

## 13. 后续演进方向

1. **把 YOLO 小模型迁移到 ESP32-P4**，PC 只做大模型调用
2. **用手机替代 PC**，实现更便携的方案
3. **加入 GPS 和地图 API**，实现真正的全局导航
4. **加入双目深度或 ToF 传感器**，获取障碍物距离
5. **引入 MCP 协议**，让大模型通过标准化接口调用各种小模型

---

## 14. 结论

本方案在现有硬件基础上，通过 **ESP32-P4 + OV5647 + ATK-MS601M 陀螺仪 + PC Agent + Qwen-VL**，实现一个功能较完整的导盲眼镜原型：

- **多目标识别**：行人、车辆、红绿灯、盲道、障碍物、斑马线、路牌
- **姿态感知**：通过 IMU 把画面目标映射到真实方向
- **局部路径引导**：有盲道沿盲道走，无盲道基于可通行区域给出转向建议
- **Agent 智能决策**：小模型快速感知，大模型处理复杂场景

核心原则：

> **小模型做感知，IMU 做方向，大模型做决策，简单场景快速响应，复杂场景智能推理。**
